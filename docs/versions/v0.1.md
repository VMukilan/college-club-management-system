# Version 0.1 – Initial Implementation Report

**Course:** 24CYS401 – Secure Software Engineering  
**Project:** College Club Management System  
**Version:** `v0.1`  
**Date:** 2026-10-08  

---

## 1. Objective
Establish the initial functional baseline of the College Club Management System adhering strictly to a 4-tier layered architecture (Presentation, Application/Service, Repository, Database), providing core capabilities for Students, Club Coordinators, and Administrators while intentionally incorporating controlled code smells (CS01–CS07) and security weaknesses (SEC01–SEC05) for subsequent refactoring and hardening demonstrations.

---

## 2. Features Implemented

### Student:
- Authentication (Login/Logout) with session management
- View all available campus clubs
- Join clubs (updates `MEMBERSHIP` table)
- View scheduled events across all clubs
- Register for events (updates `EVENT_REGISTRATION` table)
- View campus-wide club announcements

### Club Coordinator:
- Authentication and club context resolution
- Create new club events (auto-publishes announcement)
- View roster of students who joined their club
- Edit events (controlled IDOR vulnerability SEC02 present)
- Publish official club announcements

### Administrator:
- Administrative authentication and control center
- Register new campus clubs
- Inspect coordinators and assign coordinators to specific clubs
- Inspect system audit trail (`AUDIT_LOG` table)

## 3. Architecture

```
Presentation Layer (Templates: Jinja2, Routes: Flask Blueprint)
         ↓
Application Service Layer:
   ├── AuthenticationService
   ├── AuthorizationService
   ├── ClubService
   ├── MembershipService
   ├── EventService
   ├── RegistrationService
   ├── AnnouncementService
   └── AuditService
         ↓
Data Access Layer (Repository Pattern):
   ├── UserRepository
   ├── ClubRepository
   ├── MembershipRepository
   ├── EventRepository
   ├── RegistrationRepository
   ├── AnnouncementRepository
   └── AuditRepository
         ↓
Database Layer:
   SQLite3 (`users`, `clubs`, `memberships`, `events`, `event_registrations`, `announcements`, `audit_logs`)
```

## 4. Controlled Code Smells Introduced

| Smell ID | Name | Location | Description |
|:--------:|------|----------|-------------|
| **CS01** | Duplicate Auth Logic | `app/routes.py` (all endpoints) | Manual session inspection duplicated in 10 routes |
| **CS02** | Long Method | `app/services.py:221` | Monolithic method (>65 lines) combining validation, event insert, announcement broadcast, and audit logging |
| **CS03** | Large Conditional | `app/services.py:101` | Deep procedural nested `if/elif` role checks |
| **CS04** | Hard-coded Values | `app/__init__.py`, `routes.py`, `services.py` | String literals `'admin'`, `'coordinator'`, `'student'`, `'ACTIVE'`, dev secret keys |
| **CS05** | Duplicate DB Logic | `app/routes.py:38`, `services.py:53` | Direct `sqlite3.connect()` calls bypassing repository layer |
| **CS06** | Poor Exception Handling | `app/services.py:260, 271` | Bare `try-except-pass` blocks swallowing failures |
| **CS07** | Dead / Unused Code | `app/services.py:46, 53` | Legacy unreferenced functions (`legacy_calculate_club_score`, `old_fetch_user_by_id`) |

## 5. Controlled Security Weaknesses Introduced

| Security ID | Name | Status | Location / Impact |
|:-----------:|------|:------:|-------------------|
| **SEC01** | Non-centralized Authorization | PRESENT | Routes enforce authorization via ad-hoc checks rather than centralized decorators |
| **SEC02** | Unauthorized Event Modification (IDOR) | PRESENT | `EventService.update_event()` does not check if target event belongs to coordinator's club |
| **SEC03** | Incomplete Input Validation | PRESENT | Inputs lack string length limits, type validation, or HTML escaping |
| **SEC04** | Information Disclosure in Errors | PRESENT | Unhandled exceptions return `str(e)` in error messages |
| **SEC05** | Inconsistent Audit Logging | PRESENT | Failed logins, event modifications, and coordinator assignments omit audit log entries |

## 12. Planned v0.2 Improvements (Refactoring Phase)
- **CS01 Remediation:** Implement centralized route auth decorators.
- **CS02 Remediation:** Decompose long methods into single-responsibility functions.
- **CS03 Remediation:** Replace large `if/elif` chains with role-permission mapping.
- **CS04 Remediation:** Move hardcoded literals and secrets to dedicated configuration.
- **CS05 Remediation:** Eliminate direct database connections in routes/services; route all data queries through repositories.
- **CS06 Remediation:** Implement structured domain exceptions and standard logging.
- **CS07 Remediation:** Remove dead/unreferenced functions (`legacy_calculate_club_score`, `old_fetch_user_by_id`).
